Note that the new run also does *more* work per journey: it adds 6,021 polling requests on `GET /api/participations/:id` (30,945 vs 24,924) to wait for the queue. The throughput gain is real even with that extra traffic included.

### Why it got faster

`POST /answer` previously issued five sequential queries. It now issues **zero** — participation status, question grading data and duplicate detection are all served from Redis:

| Endpoint | Queries before | Queries after |
|---|---|---|
| `POST /api/participations/:id/answer` | 5 | **0** |
| `POST /api/participations/:id/finish` | 5 | **0** (enqueue only) |
| `GET /api/participations/:id` (in flight) | 2 | **0** |
| `GET /api/questions` | 3 | 3 (unchanged) |

Answers still reach PostgreSQL — the worker writes them in one batched transaction per participation using `UNNEST` plus a single `UPDATE`, instead of one `INSERT` round-trip per answer followed by four more queries.

### The bottleneck moved

`GET /health` touches no database and no cache, yet its average rose from 11.88 ms to 23.86 ms. That is the tell: with the pool contention gone, the limit is now the **single Node process's event loop**, which is serving nearly twice the traffic on one core. Recommendation 3 below (clustering) is now the highest-value change, where before it was third.

## 9. Architecture

```
POST /answer   ──► Redis  participation:{id}:answers   (HSETNX, 0 DB queries)
                   Redis  question:{id}:answer         (grading data, warmed at boot)

POST /finish   ──► snapshot answers ──► BullMQ "participation-finish" ──► 202 Accepted

  worker (in-process, concurrency 25)
        └─► one transaction:  INSERT … UNNEST … ON CONFLICT DO NOTHING
                              UPDATE participations SET status='completed'
        └─► clear answer cache, set cached status to 'completed'

GET /participations/:id ──► Redis while in flight, PostgreSQL once completed
```

Design points worth knowing:

- **`processing` is a cache-only status.** The PostgreSQL `CHECK` constraint still only ever sees `in_progress` or `completed`, so no migration was needed.
- **Duplicate answers are caught by `HSETNX`**, which is atomic — two concurrent requests for the same question cannot both win.
- **The worker is idempotent.** Answers insert with `ON CONFLICT DO NOTHING`, the participation row is taken `FOR UPDATE`, the `UPDATE` is guarded on `status <> 'completed'`, and the score is recomputed from `user_answers` rather than trusted from the job payload. A job may safely run twice.
- **The queue deduplicates** on a job id derived from the participation id, so a double-submitted finish cannot enqueue twice.
- **Redis runs `--maxmemory-policy noeviction`**, because answers are the only copy until they are flushed. Under memory pressure Redis rejects writes rather than silently dropping a user's answers.
- **Failed jobs retry** 5 times with exponential backoff and are retained for 24 hours for inspection.

### Remaining recommendations, re-ranked

1. **Run Node under `cluster`/PM2, one worker per core.** Now the top bottleneck — the event loop is saturated well before PostgreSQL or Redis are.
2. **Split the queue worker out of the API process** (`RUN_WORKER=false` on web nodes, a dedicated worker process elsewhere) so finalization cannot compete with request handling for CPU.
3. **Consider a WebSocket or SSE completion push** to replace client polling. Polling added 6,021 requests to this run; a push would remove them and drop the observed finalization lag to near the true queue latency.

## 10. Reproduce

The app must be running (`npm run dev`) with the database seeded (`npm run seed`) and both containers up (`docker compose up -d`).

```bash
# Full 500-VU run
docker run --rm -v "$PWD/k6:/scripts" -e OUT_DIR=/scripts \
  grafana/k6:latest run /scripts/stress-test.js

# Quick smoke run
docker run --rm -v "$PWD/k6:/scripts" -e OUT_DIR=/scripts \
  grafana/k6:latest run --stage 10s:5 /scripts/stress-test.js
```

Environment variables: `BASE_URL`, `ANSWERS_PER_JOURNEY` (default 5), `FINALIZE_POLL_INTERVAL` (default 0.2s), `FINALIZE_MAX_POLLS` (default 50), `OUT_DIR`.
